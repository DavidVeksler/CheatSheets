Key lifecycle

Distributed key generation

Each party contributes entropy and proves consistency; no dealer ever possesses the aggregate private key.

Concrete use: For a 2-of-3 wallet, retain the DKG transcript hash, participant identities, public key, and independently derived first address.

Failure mode: Importing and splitting a pre-existing seed leaves a full-key compromise moment.

Signing

Participants validate the same canonical payload, consume one presign package where applicable, and produce an ordinary chain signature.

Concrete use: Bind request ID wd_20260831_0042, chain ID, nonce, asset, amount, destination, fee ceiling, and policy decision into the audit record.

Failure mode: A quorum can correctly sign a malicious payload supplied by a compromised policy engine.

Proactive refresh

Shares are re-randomized while the public key and address remain unchanged; old and new epoch shares cannot be combined.

Concrete use: Refresh quarterly and after a suspected host compromise; prove completion on all three parties before deleting epoch N material.

Failure mode: A configured job that has never completed a restore test is not a control.

Resharing

A live quorum changes t-of-n or replaces participants without moving funds.

Concrete use: Replace a departing 2-of-3 signer with a new HSM and verify the unchanged public key before revoking the old share.

Failure mode: Below-threshold survivors cannot reshare; the address is permanently frozen.

Retirement

Move remaining assets, destroy every live share and presign cache, and retain non-secret audit evidence.

Concrete use: After a chain is delisted, sweep all derivation paths, reconcile zero balances, then obtain destruction attestations from each domain.

Failure mode: Deleting the vendor workspace while dust or token contracts remain creates orphaned value.

What MPC does not protect

Policy-engine compromise

The signer sees an authorized request, so threshold secrecy provides no safety.

Concrete use: Require an independently operated callback to compare the payload with ledger intent before any share acts.

Failure mode: Putting policy and all shares under one admin collapses the architecture.

Blind signing

Approvers who see only a digest cannot verify the human-readable destination or contract call.

Concrete use: Decode EIP-712 or chain-native intent on a separate trusted display and bind it to the request.

Failure mode: A green approval screen can describe different bytes than the signer receives.

Address substitution

Malware changes a destination after business approval but before canonical serialization.

Concrete use: Use allowlists with a 48-hour activation delay and out-of-band confirmation for additions.

Failure mode: Clipboard checks and prefix/suffix matching are not authentication.

Threshold insider collusion

Exactly t valid participants are sufficient by design.

Concrete use: Set role separation so two approvers cannot also administer policy or signer infrastructure.

Failure mode: 2-of-3 is not two humans if automation controls both shares.

Missing attribution

The chain records one aggregate signature, not which parties participated.

Concrete use: Write append-only participant, policy, payload, and transcript hashes to an external audit store.

Failure mode: On-chain indistinguishability trades away native signer attribution.

Supply-chain compromise

A malicious library or signer image can bias nonces, leak shares, or rewrite payloads.

Concrete use: Pin reproducible builds, SBOM, signatures, audit commit, and measured boot evidence.

Failure mode: A mathematically proven protocol does not prove the deployed binary.

Vendor due-diligence checklist

A protocol label is the start of diligence, not the result.

  1. □ Name the protocol, revision, ciphersuite, implementation commit, and every production audit.
  2. □ Prove DKG was used; document any full-key import path and when it is allowed.
  3. □ Map shares to independent IAM, cloud, region, operator, HSM, backup, and update domains.
  4. □ Show completed refresh and resharing evidence, not configuration screenshots.
  5. □ Explain malformed-proof validation, nonce handling, presign reuse prevention, and identifiable abort.
  6. □ Separate policy administration from signer administration and require quorum for policy changes.
  7. □ Provide an export/exit package and execute a restore in an isolated environment.
  8. □ Measure signing availability for the chosen quorum; alert before survivors fall below threshold.
  9. □ Retain payload and participant attribution outside the vendor's trust domain.
  10. □ Test vendor disappearance, customer-share loss, cloud outage, and revoked operator scenarios.

Common mistakes & anti-patterns

Seed import called MPC

Splitting a key after creation is secret sharing, not dealerless generation.

Concrete use: Mark imported wallets as a distinct assurance class.

Failure mode: Marketing vocabulary cannot erase the full-key event.

One-manager quorum

Multiple accounts still share one coercion and employment boundary.

Concrete use: Require independent reporting lines for high-value tiers.

Failure mode: Org-chart correlation defeats technical separation.

ECDSA-only selection

ECDSA threshold families do not sign Ed25519-native chains.

Concrete use: Inventory chain signature schemes before procurement.

Failure mode: Raw signing may bypass transaction parsing and policy.

No exit rehearsal

Exportability exists only if a second implementation can restore and sign.

Concrete use: Run an annual isolated restore using the contractual package.

Failure mode: A PDF procedure is not evidence of recoverability.
